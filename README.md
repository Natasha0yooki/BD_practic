# 1. Назначение проекта

Проект представляет собой реляционную базу данных для хранения, систематизации и аналитической обработки информации о кредитных заявках Lending Club.

Исходные данные представлены двумя CSV-файлами: первый содержит сведения о принятых кредитных заявках и выданных кредитах, второй — об отклонённых заявках.

Изначально данные представлены в плоском формате: множество характеристик заявки, заёмщика, кредитной истории и обслуживания кредита находятся в одной таблице.

Для устранения избыточности и повышения целостности данных разработана реляционная структура PostgreSQL, состоящая из девяти таблиц.

Основные задачи базы данных:

- Хранение информации о кредитных заявках.
- Хранение характеристик заявителей.
- Хранение показателей кредитной истории.
- Учёт выданных кредитов и их параметров.
- Хранение информации об обслуживании задолженности.
- Учёт программ финансовых трудностей (Hardship).
- Учёт урегулирования задолженности (Settlement).
- Хранение информации об отклонённых заявках.
- Подготовка данных для аналитических запросов и оценки кредитных рисков.

База данных предназначена для аналитиков данных, разработчиков, специалистов по кредитным рискам и исследователей финансового рынка.

# 2. Источники данных

## 2.1. Accepted — принятые заявки

Файл:

`accepted_2007_to_2018Q4.csv`

Содержит сведения о принятых кредитных заявках и выданных кредитах.

Основные группы данных:

| Группа | Примеры атрибутов |
|---|---|
| Идентификация кредита | `id` |
| Параметры заявки | `loan_amnt`, `term`, `purpose`, `title` |
| Данные заявителя | `emp_title`, `emp_length`, `home_ownership` |
| Финансовые показатели | `annual_inc`, `dti` |
| Кредитная история | `fico_range_low`, `fico_range_high`, `delinq_2yrs` |
| Параметры кредита | `funded_amnt`, `int_rate`, `installment` |
| Обслуживание кредита | `total_pymnt`, `total_rec_prncp`, `recoveries` |
| Финансовые трудности | `hardship_flag`, `hardship_type` |
| Урегулирование задолженности | `debt_settlement_flag`, `settlement_status` |

Данные из этого файла распределяются между восемью таблицами основной структуры, а также справочником кредитных грейдов.

## 2.2. Rejected — отклонённые заявки

Файл:

`rejected_2007_to_2018Q4.csv`

Содержит информацию о заявках, которые не были приняты кредитной организацией.

Основные атрибуты:

| Атрибут CSV | Назначение |
|---|---|
| `Amount Requested` | Запрашиваемая сумма кредита |
| `Application Date` | Дата подачи заявки |
| `Loan Title` | Назначение или название кредита |
| `Risk_Score` | Оценка риска |
| `Debt-To-Income Ratio` | Соотношение долговой нагрузки к доходу |
| `Zip Code` | Почтовый индекс |
| `State` | Штат |
| `Employment Length` | Стаж работы |
| `Policy Code` | Код политики |

Все данные из этого файла помещаются в отдельную таблицу `rejected_application`.

Отклонённые заявки не связываются с `loan_application`, поскольку в исходных файлах отсутствует гарантированный общий идентификатор, позволяющий установить соответствие конкретной отклонённой заявки конкретному выданному кредиту.

# 3. Архитектура базы данных

База данных состоит из девяти таблиц.

| № | Таблица | Назначение |
|---|---|---|
| 1 | `loan_grade` | Справочник кредитных грейдов |
| 2 | `loan_application` | Информация о принятой кредитной заявке |
| 3 | `applicant_profile` | Характеристики заявителя |
| 4 | `credit_profile` | Кредитная история заявителя |
| 5 | `loan` | Информация о выданном кредите |
| 6 | `loan_performance` | Показатели обслуживания кредита |
| 7 | `hardship` | Информация о финансовых трудностях |
| 8 | `settlement` | Информация об урегулировании задолженности |
| 9 | `rejected_application` | Информация об отклонённых заявках |

## 3.1. Общая логика связей

Центральной сущностью является `loan_application`.

С ней связаны:
- `applicant_profile` — профиль заявителя;
- `credit_profile` — кредитная история;
- `loan` — выданный кредит.

С таблицей `loan` связаны:
- `loan_grade` — справочник грейдов;
- `loan_performance` — показатели обслуживания;
- `hardship` — финансовые трудности;
- `settlement` — урегулирование задолженности.

`rejected_application` является самостоятельной таблицей.

### Кардинальности связей

| Родительская таблица | Дочерняя таблица | Тип связи |
|---|---|---|
| `loan_application` | `applicant_profile` | 1:0..1 |
| `loan_application` | `credit_profile` | 1:0..1 |
| `loan_application` | `loan` | 1:0..1 |
| `loan_grade` | `loan` | 1:N |
| `loan` | `loan_performance` | 1:0..1 |
| `loan` | `hardship` | 1:0..1 |
| `loan` | `settlement` | 1:0..1 |

Связи 1:0..1 обеспечиваются ограничениями `UNIQUE` на внешних ключах дочерних таблиц.

Это означает, что одной заявке или кредиту соответствует не более одной записи в каждой связанной таблице.

# 4. Подробное описание таблиц

## 4.1. loan_grade — справочник кредитных грейдов

**Назначение:** хранение допустимых категорий кредитного рейтинга Lending Club.

Грейд определяет категорию риска заёмщика, а подгрейд уточняет её.

Примеры:
- A1;
- A2;
- B3;
- C5;
- G1.

| Атрибут | Тип | Обязательность | Назначение |
|---|---|---|---|
| `grade` | CHAR(1) | Да | Основной грейд A–G |
| `sub_grade` | CHAR(2) | Да | Подгрейд A1–G5 |

**Первичный ключ:** `(grade, sub_grade)`.

Ограничения:
- `grade` принимает только значения A–G.
- `sub_grade` принимает только значения A1–G5.
- Первая буква `sub_grade` должна совпадать с `grade`.

Связь: одна запись справочника может использоваться многими кредитами.

Перед загрузкой кредитов справочник необходимо заполнить всеми 35 допустимыми комбинациями.

## 4.2. loan_application — заявка на кредит

**Назначение:** центральная таблица, хранящая основные характеристики принятой кредитной заявки.

Именно эта таблица объединяет информацию о заявителе, кредитной истории и выданном кредите.

| Атрибут | Тип | Обязательность | Назначение |
|---|---|---|---|
| `application_id` | BIGSERIAL | Да | Внутренний PK заявки |
| `loan_amnt` | NUMERIC(12,2) | Да | Запрашиваемая сумма |
| `term` | SMALLINT | Да | Срок кредита в месяцах |
| `purpose` | VARCHAR(50) | Нет | Цель кредита |
| `title` | VARCHAR(200) | Нет | Название кредита |
| `application_type` | VARCHAR(20) | Нет | Тип заявки |
| `issue_date` | DATE | Да | Дата выдачи кредита |
| `description` | TEXT | Нет | Описание кредита |
| `url` | TEXT | Нет | Ссылка на запись кредита |

**Первичный ключ:** `application_id`.

Ограничения:
- `loan_amnt > 0`;
- `term` принимает значения 36 или 60;
- `application_type` принимает значения `Individual` или `Joint App`.

Особенность:

В исходном CSV поле `issue_d` обозначает месяц выдачи кредита. В целевой таблице оно переименовано в `issue_date`.

При преобразовании рекомендуется использовать первое число соответствующего месяца.

Например:

`Dec-2015` → `2015-12-01`.

`application_id` является внутренним идентификатором базы данных. Он не совпадает с исходным идентификатором Lending Club.

## 4.3. applicant_profile — профиль заявителя

**Назначение:** хранение социально-экономических характеристик заявителя.

Таблица отделена от заявки для логического разделения информации о кредите и информации о заёмщике.

| Атрибут | Тип | Обязательность | Назначение |
|---|---|---|---|
| `profile_id` | BIGSERIAL | Да | PK профиля |
| `application_id` | BIGINT | Да | FK на заявку |
| `emp_title` | VARCHAR(150) | Нет | Должность |
| `emp_length` | VARCHAR(20) | Нет | Стаж работы |
| `home_ownership` | VARCHAR(20) | Нет | Тип владения жильём |
| `annual_inc` | NUMERIC(12,2) | Нет | Годовой доход |
| `verification_status` | VARCHAR(30) | Нет | Статус проверки дохода |
| `addr_state` | CHAR(2) | Нет | Штат проживания |
| `zip_code` | VARCHAR(10) | Нет | Почтовый индекс |

**Первичный ключ:** `profile_id`.

**Внешний ключ:** `application_id → loan_application.application_id`.

Ограничение `UNIQUE` на `application_id` обеспечивает связь 1:0..1.

Особенности:
- `annual_inc` не может быть отрицательным.
- `emp_length` ограничен перечнем допустимых категорий.
- `home_ownership` ограничен известными категориями.
- `verification_status` принимает три допустимых значения.

`zip_code` хранится как строка, поскольку почтовые индексы могут содержать ведущие нули.

## 4.4. credit_profile — кредитная история

**Назначение:** хранение характеристик кредитной истории заявителя на момент оформления кредита.

Эта таблица используется для анализа кредитоспособности и оценки риска.

| Атрибут | Тип | Обязательность | Назначение |
|---|---|---|---|
| `credit_profile_id` | BIGSERIAL | Да | PK |
| `application_id` | BIGINT | Да | FK на заявку |
| `dti` | NUMERIC(6,2) | Нет | Долговая нагрузка |
| `delinq_2yrs` | SMALLINT | Нет | Просрочки за последние 2 года |
| `earliest_cr_line` | DATE | Нет | Дата открытия самой ранней кредитной линии |
| `fico_range_low` | SMALLINT | Нет | Нижняя граница FICO |
| `fico_range_high` | SMALLINT | Нет | Верхняя граница FICO |
| `inq_last_6mths` | SMALLINT | Нет | Запросы кредитной истории за 6 месяцев |
| `open_acc` | SMALLINT | Нет | Количество открытых счетов |
| `pub_rec` | SMALLINT | Нет | Публичные записи |
| `revol_bal` | NUMERIC(12,2) | Нет | Остаток револьверной задолженности |
| `revol_util` | NUMERIC(7,2) | Нет | Использование револьверного лимита |
| `total_acc` | SMALLINT | Нет | Общее количество счетов |

**Первичный ключ:** `credit_profile_id`.

**Внешний ключ:** `application_id → loan_application.application_id`.

Ограничения:
- DTI не может быть отрицательным.
- Количество просрочек и счетов не может быть отрицательным.
- FICO должен находиться в диапазоне 300–850.
- Нижняя граница FICO не должна превышать верхнюю.
- Револьверная задолженность не может быть отрицательной.
- `revol_util` не может быть отрицательным.

Важно: для `revol_util` в текущей версии нет верхней границы 100. Это сделано намеренно до проверки фактических значений исходного CSV.

## 4.5. loan — выданный кредит

**Назначение:** хранение основных параметров кредита, который был выдан заявителю.

Таблица связывает заявку с конкретным кредитом и содержит его финансовые характеристики.

| Атрибут | Тип | Обязательность | Назначение |
|---|---|---|---|
| `loan_id` | BIGINT | Да | Исходный ID кредита, PK |
| `application_id` | BIGINT | Да | FK на заявку |
| `funded_amnt` | NUMERIC(12,2) | Да | Фактически профинансированная сумма |
| `funded_amnt_inv` | NUMERIC(12,2) | Нет | Сумма финансирования инвесторами |
| `int_rate` | NUMERIC(5,2) | Нет | Процентная ставка |
| `installment` | NUMERIC(10,2) | Нет | Ежемесячный платёж |
| `grade` | CHAR(1) | Да | Грейд |
| `sub_grade` | CHAR(2) | Да | Подгрейд |
| `loan_status` | VARCHAR(50) | Да | Статус кредита |
| `pymnt_plan` | CHAR(1) | Нет | Признак платёжного плана |
| `initial_list_status` | CHAR(1) | Нет | Первоначальный статус листинга |

**Первичный ключ:** `loan_id`.

**Внешние ключи:**
- `application_id → loan_application.application_id`;
- `(grade, sub_grade) → loan_grade(grade, sub_grade)`.

Ограничения:
- `funded_amnt >= 0`;
- `funded_amnt_inv >= 0`;
- `int_rate` от 0 до 100;
- `installment > 0`;
- `pymnt_plan` принимает `y` или `n`;
- `initial_list_status` принимает `f` или `w`.

Для `pymnt_plan` предусмотрено значение по умолчанию `n`.

`loan_id` берётся из исходного идентификатора `id` файла accepted CSV. Он сохраняется для возможности сопоставления исходных и загруженных данных.

Важно: в текущей версии таблицы отсутствует `disbursement_method`. Его добавление можно согласовать отдельно.

## 4.6. loan_performance — показатели обслуживания кредита

**Назначение:** хранение агрегированных показателей платежей и состояния задолженности по выданному кредиту.

Таблица позволяет анализировать:
- сумму произведённых платежей;
- возврат основного долга;
- процентные платежи;
- штрафы;
- взыскания;
- остаток задолженности;
- изменение кредитного рейтинга.

| Атрибут | Тип | Обязательность | Назначение |
|---|---|---|---|
| `performance_id` | BIGSERIAL | Да | PK |
| `loan_id` | BIGINT | Да | FK на кредит |
| `total_pymnt` | NUMERIC(12,2) | Нет | Общая сумма платежей |
| `total_pymnt_inv` | NUMERIC(12,2) | Нет | Платежи инвесторам |
| `total_rec_prncp` | NUMERIC(12,2) | Нет | Полученный основной долг |
| `total_rec_int` | NUMERIC(12,2) | Нет | Полученные проценты |
| `total_rec_late_fee` | NUMERIC(10,2) | Нет | Полученные штрафы |
| `recoveries` | NUMERIC(12,2) | Нет | Взысканные средства |
| `collection_recovery_fee` | NUMERIC(10,2) | Нет | Комиссия за взыскание |
| `last_pymnt_d` | DATE | Нет | Дата последнего платежа |
| `last_pymnt_amnt` | NUMERIC(10,2) | Нет | Сумма последнего платежа |
| `next_pymnt_d` | DATE | Нет | Дата следующего платежа |
| `out_prncp` | NUMERIC(12,2) | Нет | Остаток основного долга |
| `out_prncp_inv` | NUMERIC(12,2) | Нет | Остаток долга инвесторов |
| `last_credit_pull_d` | DATE | Нет | Дата последнего получения кредитной истории |
| `last_fico_range_low` | SMALLINT | Нет | Нижняя граница последнего FICO |
| `last_fico_range_high` | SMALLINT | Нет | Верхняя граница последнего FICO |

**Первичный ключ:** `performance_id`.

**Внешний ключ:** `loan_id → loan.loan_id`.

Ограничение `UNIQUE` обеспечивает не более одной агрегированной записи обслуживания на кредит.

Важно: это агрегированные показатели из исходного датасета, а не журнал отдельных транзакций. Таблица не содержит истории каждого отдельного платежа.

## 4.7. hardship — финансовые трудности

Таблица содержит сведения о финансовых трудностях и специальных условиях погашения кредита.

| Атрибут | Тип | Обязательность | Назначение |
|---|---|---|---|

| `loan_id` | BIGINT | Да | FK на кредит |
| `hardship_flag` | CHAR(1) | Нет | Признак Hardship |
| `hardship_type` | VARCHAR(50) | Нет | Тип программы |

- Дата окончания программы не может быть раньше даты начала.

Таблица имеет связь 1:0..1 с `loan`.

При загрузке важно учитывать, что не все кредиты участвуют в программе Hardship. Отсутствие записи не означает автоматически наличие финансовых трудностей.

## 4.8. settlement — урегулирование задолженности

**Назначение:** хранение сведений о процедурах урегулирования задолженности по кредитам.

Таблица позволяет анализировать:
- наличие процедуры урегулирования;
- статус процедуры;
- дату урегулирования;
- согласованную сумму;
- процент урегулирования;
- продолжительность процедуры.

| Атрибут | Тип | Обязательность | Назначение |
|---|---|---|---|
| `settlement_id` | BIGSERIAL | Да | PK |
| `loan_id` | BIGINT | Да | FK на кредит |
| `debt_settlement_flag` | CHAR(1) | Нет | Признак урегулирования |
| `settlement_status` | VARCHAR(50) | Нет | Статус процедуры |
| `settlement_date` | DATE | Нет | Дата урегулирования |
| `settlement_amount` | NUMERIC(12,2) | Нет | Сумма урегулирования |
| `settlement_percentage` | NUMERIC(5,2) | Нет | Процент урегулирования |
| `settlement_flag_date` | DATE | Нет | Дата установки признака |
| `settlement_term` | SMALLINT | Нет | Срок урегулирования |

**Первичный ключ:** `settlement_id`.

**Внешний ключ:** `loan_id → loan.loan_id`.

Ограничения:
- `debt_settlement_flag` принимает Y или N.
- Сумма урегулирования не может быть отрицательной.
- Процент урегулирования находится в диапазоне 0–100.
- Срок урегулирования должен быть положительным.

Таблица связана с `loan` отношением 1:0..1.

# 5. Типы данных и принципы их выбора

При разработке схемы использованы типы PostgreSQL с учётом характера исходных данных.

| Тип | Где применяется | Причина выбора |
|---|---|---|
| BIGSERIAL | Внутренние идентификаторы | Автоматическая генерация PK |
| BIGINT | Исходный loan ID и FK | Большой диапазон целых чисел |
| SMALLINT | Сроки, количество счетов, баллы и признаки | Экономия места |

| TEXT | Описание и URL | Переменная длина |

Денежные значения хранятся в NUMERIC, поскольку использование FLOAT может приводить к погрешностям округления.

Почтовые индексы хранятся в VARCHAR, поскольку это идентификаторы, а не числовые показатели.

В каждой таблице предусмотрен первичный ключ.

## 6.2. Внешние ключи

| Таблица | Поле FK | Ссылка |
|---|---|---|
| applicant_profile | application_id | loan_application.application_id |
| credit_profile | application_id | loan_application.application_id |
| loan | application_id | loan_application.application_id |

## 6.3. Правила удаления

В схеме используются следующие правила:

**ON DELETE CASCADE**

Применяется для:
- applicant_profile;
- credit_profile;
- loan_performance;
- hardship;
- settlement.

При удалении родительской записи автоматически удаляются связанные дочерние записи.

**ON DELETE RESTRICT**

Применяется для связи `loan` с `loan_application`.

Удаление заявки запрещается, если с ней связан выданный кредит.

Эти правила защищают целостность данных.

# 7. Ограничения целостности

В базе применяются следующие виды ограничений.

| Ограничение | Назначение | Пример |
|---|---|---|
| PRIMARY KEY | Уникальная идентификация строки | application_id |
| FOREIGN KEY | Контроль связей между таблицами | loan_id |
| UNIQUE | Запрет повторения значения | application_id в applicant_profile |
| NOT NULL | Запрет отсутствующих значений | loan_amnt |
| CHECK | Проверка допустимых значений | term IN (36, 60) |
| DEFAULT | Значение по умолчанию | pymnt_plan = 'n' |

Ограничения CHECK предназначены для контроля корректности данных при вставке и обновлении.

Важно: CHECK с NULL обычно не запрещает запись, поэтому обязательность поля дополнительно определяется через NOT NULL.

# 8. Индексы

В схеме предусмотрены индексы для ускорения аналитических запросов.

| Индекс | Таблица | Тип | Назначение |
|---|---|---|---|
| idx_loan_status | loan | B-tree | Фильтрация по статусу |
| idx_loan_grade | loan | B-tree | Анализ по грейдам |
| idx_application_issue_d | loan_application | B-tree | Поиск по дате выдачи |
| idx_application_issue_brin | loan_application | BRIN | Диапазонный анализ дат |
| idx_rejected_date_brin | rejected_application | BRIN | Диапазонный анализ отклонённых заявок |
| idx_rejected_risk_score | rejected_application | B-tree | Фильтрация по риск-баллу |
| idx_rejected_state | rejected_application | B-tree | Анализ по штатам |

Также PostgreSQL автоматически создаёт уникальные индексы для первичных ключей и ограничений UNIQUE.

Отдельные индексы для внешних ключей, уже покрытых UNIQUE, в данной схеме не создаются.

**Примечание по BRIN:** эффективность этих индексов зависит от физического порядка строк и корреляции с датами. После загрузки необходимо проверить производительность запросов с помощью EXPLAIN ANALYZE.

## 11.4. Средняя долговая нагрузка по грейдам

```sql
SELECT
    l.grade,
    ROUND(AVG(cp.dti), 2) AS avg_dti,
    COUNT(*) AS loan_count
FROM credit.loan l
JOIN credit.loan_application a
    ON l.application_id = a.application_id
JOIN credit.credit_profile cp
    ON a.application_id = cp.application_id

ORDER BY l.grade;
```

## 11.5. Доля кредитов с финансовыми трудностями

```sql
SELECT
    COUNT(*) AS total_loans,
    COUNT(h.loan_id) AS hardship_loans,
    ROUND(
        COUNT(h.loan_id) * 100.0 / NULLIF(COUNT(*), 0),
        2
    ) AS hardship_percentage
FROM credit.loan l
LEFT JOIN credit.hardship h
    ON l.loan_id = h.loan_id;
```

## 11.6. Сравнение принятых и отклонённых заявок

```sql
SELECT
```

Важно: это сравнение количества записей в двух файлах, а не расчёт реальной вероятности одобрения заявки. Для корректной оценки approval rate необходимо учитывать особенности формирования выборок и временные периоды.

# 13. Ограничения текущей модели

Текущая структура является нормализованной аналитической моделью, но не охватывает все 151 атрибут исходного accepted CSV.

Осознанные особенности модели:

1. Нет отдельной таблицы клиентов, поскольку отсутствует надёжный заполненный идентификатор заёмщика.
2. Нет отдельной таблицы второго заявителя для Joint App.
3. Не хранится история каждого отдельного платежа.
4. Не все дополнительные характеристики кредитной истории включены в `credit_profile`.
5. Отклонённые заявки хранятся отдельно от принятых.
6. `loan_performance` содержит агрегированные показатели, а не транзакционный журнал.
7. `issue_date` хранит месяц выдачи кредита в формате DATE.

Перед расширением структуры необходимо определить, какие дополнительные атрибуты действительно нужны для аналитических задач.
